# v0.2 engineering prompt

The brief for the next iteration, written as the instructions a principal engineer would
hand to an implementer. Every item has acceptance criteria; nothing ships without a test.

## Context

v0.1 works end to end and is published. Its biggest practical cost is the run count: a
real replay at the recommended 4 runs per side is 8 paid agent runs every time, even
when the regression is obvious after a few. Research supports fixing this with
sequential testing: AgentAssay (arXiv 2603.02601) adapts sequential probability ratio
testing to agent workflows to cut cost while keeping error rates. Releases also still
need a human passkey per publish, and the report cannot show what an individual run did.

## Goals

### 1. Adaptive run counts: `--runs auto`

Stop replaying as soon as the answer is clear, without inflating false positives.

- Group-sequential design with Bonferroni alpha spending: K planned looks, each tested at
  `alpha / K`. Pick the smallest consistent K such that the first look is the minimum N
  at which `alpha / K` is reachable, then a look every 2 runs, plus a final look at
  `--max-runs` (default 8). For alpha 0.05 and max 8 this gives looks at 5, 7, 8 runs per
  side at alpha 0.0167 each.
- Arms run interleaved in rounds (control, candidate, control, ...), so slow drift in
  the API or the machine is not mistaken for a model effect.
- Stop early when (a) a hard regression is confirmed at the per-look alpha, or (b) no
  adverse effect is present even weakly (no hard finding, no soft change past the
  threshold): continuing could only find a regression the data does not hint at.
  Otherwise continue to the next look.
- The report states the design: looks, per-look alpha, where it stopped and why.
- `--dry-run` shows the best case (first look) and worst case (max runs) cost.

Acceptance: the stopping rule is a pure function with table-driven tests (clear
regression stops at the first look, clear no-change stops at the first look, ambiguous
continues to the max); the look plan is tested for several alpha/max combinations; an
end-to-end test with the scripted agent stops at 5 runs per side for the demo regression
and saves 6 of 16 runs; fixed `--runs N` behaves exactly as before.

### 2. Releases without a passkey: trusted publishing

- `.github/workflows/release.yml`, triggered when a GitHub Release is published: install
  a current npm (trusted publishing needs npm 11.5+), run the full check, build, then
  `npm publish --provenance --access public` with `id-token: write` and no token secret.
- `RELEASING.md` documents the one-time step on npmjs.com (link the package to this
  repository and workflow) and the release checklist.

Acceptance: the workflow is valid YAML with least-privilege permissions; nothing runs on
ordinary pushes; docs state the one manual prerequisite plainly.

### 3. See what each run did

- In the HTML report, each run in the Runs section expands to its ordered steps (tool,
  target, error marker), capped at 80 steps with a "+N more" line. Still no scripts:
  native `<details>` elements only.

Acceptance: a test asserts per-run steps render, are escaped, and are capped.

### 4. Faster `scan` (measured, then rejected)

Bounded-concurrency parsing was implemented and measured on 40 real sessions: 2.70 s
before, 2.61 s after (about 3%, within noise). Parsing is CPU-bound JSON work on one
thread, so overlapping file reads cannot help much. The change was reverted: it added
complexity for no real gain. Worker-thread parsing is on the roadmap.

## Non-goals (recorded in the roadmap)

- A second agent adapter: no real transcripts of another agent exist on the author's
  machine, and the project rule is to never invent a file format.
- Model-graded comparison of final answers (opt-in, costs money, later).

## Definition of done

`pnpm check` green, CI and the Action self-test green on Linux and Windows, docs and
changelog updated, version 0.2.0 prepared (publishing stays a maintainer action).
